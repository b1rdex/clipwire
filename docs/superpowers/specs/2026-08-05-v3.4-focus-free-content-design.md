# v3.4 — focus-free content, for text

Date: 2026-08-05. Supersedes v3.3's §7 (see §2.1).

Every number in this document was measured on the target machine on 2026-08-05 and is sourced at
the point it is used. Where something is inferred rather than measured, the sentence says so.

---

## 1. The problem, as measured

### 1.1 v3.3 removed one of three focus thefts, and shipped believing it had removed the problem

v3.3 moved *change detection* off `wl-paste` and on to GPaste's history uuid over D-Bus. It was
merged, deployed and verified — and the desktop still blinks on every copy. The owner reported it
the same day, in both directions:

> «при копировании экран моргает… без разницы, копирую на маке или на пк… копи, далее блинк
> (появляется на микро момент иконка на панели приложений и забирает фокус), далее возврат фокуса
> где и был»

**"In both directions" is the whole clue.** On a Mac→PC copy the agent runs no `wl-paste` at all,
so the read path cannot be the only source. There are three, and v3.3 addressed one:

| path | what runs on the PC | steals focus |
|---|---|---|
| noticing a PC-side copy | `gpaste_history_uuid` over D-Bus (v3.3) | no |
| fetching a PC-side copy | `Clipboard.read()` → **two** `wl-paste` invocations | **yes** |
| landing a Mac-side copy | `Clipboard.write()` → `wl-copy` | **yes** |

The mechanism is the same on both remaining rows and was never written down for `wl-copy`: with no
`wlr-data-control` on this compositor, a client needs a serial from an input event to call
`set_selection`, so it must create a surface and take focus. That surface is the icon the owner
sees appear in the app panel.

### 1.2 The A/B that settled it, and the two ways it would have lied

Ten writes per phase, 2 s apart, phases unlabelled until the owner had answered both:

- **Phase 1, `wl-copy`** → «мигает».
- **Phase 2, GPaste `Add` over D-Bus** → «не мигает».

Two controls make that a measurement rather than an impression:

1. **The agent was stopped for the test**, verified by `pgrep -c` → 0 rather than assumed. With it
   running, *any* write to the PC clipboard makes the agent notice and call `read()` — two
   `wl-paste` invocations — so **both phases would have blinked from the agent's own read-back**,
   and the test would have measured nothing.
2. **A passive observer recorded 10 uuid changes in each phase, 24 bytes each.** Without it,
   "phase 2 did not blink" and "phase 2 did nothing" are the same reading. The observer never
   invokes `wl-*` (it does not import `subprocess`) and never records a clipboard body.

### 1.3 The blocker that had to clear first

`Add` moving GPaste's *history* is not the same as moving the *Wayland selection*; a paste on the
PC could still have produced the old text. Measured: after `printf … | gpaste-client add`,
`wl-paste -n --type text/plain` returns **exactly the added text**. The approach is sound.

### 1.4 What the replacement costs, measured over a held connection

| call | cost |
|---|---|
| `GetRawElement` / `GetElementAtIndex` (read) | **0.1 ms** |
| `Select(uuid)` | sub-ms |
| `Add`, content already at the top of history (dedup) | **0.4 ms** |
| `Add`, **novel** content | **1.37 s — flat: 1.3704–1.3843 over six runs** |

The same `add` through `gpaste-client` took **1.4059 s**, so the wait is inside GPaste, not in the
transport. Its flatness says it is a fixed wait rather than work proportional to the payload;
GPaste's source puts it in `clipboards_manager_select`, which this project has **not** verified —
that attribution is inferred.

**The owner accepted the ~1.4 s.** A clip typed on the Mac lands on the PC 1.4 s later than today,
against a person who takes longer than that to turn their head.

## 2. Scope

**In:** text, both directions, on a machine where GPaste is available.

**Out:** images, the no-GPaste machine, and every read that has no uuid to route by (§5).

### 2.1 This lifts v3.3 §7, deliberately and by name

v3.3 §7 is titled *"Non-goal: reading content from GPaste"* and its plan repeats the rule as
"Nothing in this plan may fetch clip bodies from GPaste." **v3.4 lifts it for text.** The reason it
can be lifted is the reason it existed: v3.3 had no evidence that a non-blinking source of clip
*bodies* existed, and now there is one, measured. Without `wlr-data-control` there is no other.

### 2.2 Images stay on `wl-clipboard` — on scope, NOT on impossibility

An earlier reading of this cycle held that image bytes were reachable only by parsing GPaste's
private `history.xml`. **That is false, and the record must not carry it:** an image item's value
*is the path to the PNG*, so `GetRawElement(uuid)` returns that path and the file is readable
directly. Images are out of v3.4 because the owner scoped them out, and because the v3.2 provenance
machinery — built on "hash the bytes you read back, never the bytes you wrote", because GPaste
re-encodes images and moves 398 267 of 614 400 bytes on a real screenshot — deserves its own cycle
rather than a passenger seat in this one.

**Consequence, stated so it is not rediscovered as a defect: copying an image still blinks, in both
directions.**

### 2.3 The no-GPaste machine is untouched BY CONSTRUCTION

v3.3 §2 requires that a machine with no GPaste keeps today's behaviour exactly. This spec satisfies
it the same way v3.3 did, and for the same reason: **the new unit is constructed only in the
`GPasteWatcher` branch of `make_watcher`**, so on a machine without GPaste it does not exist at all.
`WaylandClipboard` (`agent/clipwire-agent.py:2795–3122`) is not modified by a single line — "exactly
today's behaviour" is literally today's code.

This project has already shipped a fix sited in a watcher that is never constructed on the target
machine. This is the mirror of that trap and the same sentence prevents both.

## 3. The design

### 3.1 One small unit, two methods, no strategy pattern

```
read_text(uuid)  -> bytes | None      # None means NOT MEASURED: caller falls back
write_text(body) -> bool              # False means NOT DONE: caller falls back
```

Constructed only where §2.3 says. Both call sites in the existing agent get **one guard clause**
each — tier present and this is text → tier; `None`/`False` → the existing `wl-clipboard` code,
unchanged.

**No strategy/abstraction layer.** `WaylandClipboard` is already 328 lines carrying 89 lines of
code; the file as a whole is 6 648 lines carrying ~1 100. An abstraction here is a magnet for the
prose this project has measured a defect rate on — seven of fourteen tasks in one release shipped
correct code with a false comment. Two guarded paths are cheaper to read than one indirection.

### 3.2 Read — route by kind first, then take the body raw

The watcher already holds the uuid (that is v3.3's fast tier). So:

1. `GetElementKind(uuid)` → **only `Text` takes the new path.** `Image`, `Uris`, `Password` and
   any unrecognised kind fall through to `Clipboard.read()`.
2. Body via **`GetRawElement`** (`gpaste-client --raw get <uuid>`), never `GetElementAtIndex`.

Step 1 is not defensive decoration. `GetElementAtIndex` returns the **display** string, so without
the kind check an image at the top of the history sends the Mac the literal text
`[Image, 1686 x 1182 (08/05/26 15:51:35)]` — a clip that is wrong rather than missing, which is the
worse failure.

Step 2 avoids a second bug class: `gdbus call` prints a GVariant, so a body would arrive with
`\'`, `\\`, `\n` and `\uXXXX` escaping that has to be parsed back out of arbitrary user text.
`--raw get` prints the value with no added newline and no escaping.

**2026-08-17, final review — the read guard declines the tier on a probe-provoked observation.**
An observation can be raised by the safety net's own `probe()` token moving while the history uuid
stands still. That pair means GPaste **recorded nothing**: an app it excludes, a password manager,
its own image re-offer. The top of its history is then somebody else's older clip, so routing that
observation through the tier answers with the *wrong* content rather than with none — either
swallowed as an echo of what was already sent, or sent stale. `wl-paste` is the only reader that
can see such a clip, so `_observe_tick` raises a one-shot the read guard consumes before it fetches
a uuid, and the observation falls through to `Clipboard.read()`. This keeps v3.3 §4.2's contract —
*"the slow tier always feeds the worker, not only the judge, so clips GPaste fails to track still
sync at the slow cadence"* — for the clips it can see: **this class blinks, at the probe cadence,
as it did before v3.4.**

**The guard's window, named here rather than rediscovered as a defect: a tracked copy can shadow an
untracked one for a tick.** `uuid_frozen` compares the history uuid against its value at the
PREVIOUS slow tick, so the guard fires only when that uuid stood still across the *entire*
`SAFETY_NET_POLL_SECONDS` window — which means an untracked clip that lands within one window of a
tracked copy sees a uuid that moved, raises no flag, is answered from history, and is still silently
lost, where pre-v3.4 `wl-paste` would have synced it at that tick. That is a strictly narrower
residual than the defect it fixes, which lost *every* untracked clip; it is accepted rather than
widened, because acting on a single unconfirmed tick is what a one-shot can do, and widening it
means holding a suspicion across ticks — v3.3 §4.2 already weighed that trade for the verdict and
left it alone.

The cost of the guard is one extra `wl-paste` fork, never wrong content, and it has two sources.
The signal is raised after the poller has already set the shared event, so a worker that wins that
race leaves one observation on the old behaviour and spends the flag on the next one. And
structurally, at `FAST_TIER_SECONDS` = 5 s the uuid reading lags: a tracked copy landing between two
fast ticks leaves `_last_uuid` stale at the slow tick, so the flag is raised on an ordinary tracked
copy and that copy takes a focus-taking fork it did not need.

### 3.3 Write — content goes on stdin, NEVER on a command line

The agent spawns `gpaste-client add` with `stdin=PIPE`, writes the body to that pipe and closes it.
No shell, no `printf`, no argument carrying content. (The shell form `printf … | gpaste-client add`
appears in this cycle's probe scripts and is the same route by hand; the agent must not shell out,
because a shell adds a quoting layer to arbitrary user text for no gain.)

**`gdbus call … Add "<text>"` is not an option, and not on taste — it is functionally broken.**
Linux caps one argument at `MAX_ARG_STRLEN` = 128 KiB, while the agent's own `MAX_TEXT_BYTES`
(`agent/clipwire-agent.py:39`) is 4 194 304. A clip between those two sizes gives `E2BIG` and the
write never happens. And a clipboard routinely holds passwords and tokens: on the argv route they
sit in world-readable `/proc/<pid>/cmdline` for the whole 1.4 s the call blocks.

Measured: a **200 KiB** clip lands intact through stdin — a size at which the argv route is already
dead.

### 3.4 The read-back check, and the fallback it arms

**After every `add`, re-read the top of the history and compare it with what was written. On a
mismatch, write the clip with `wl-copy` instead and log it.**

This is not belt-and-braces. GPaste refuses silently in at least three ways, one of them measured
here:

- **Over `max-text-item-size` the clip is dropped without a word.** On this machine that setting is
  **1 048 575 bytes (1 MiB − 1)** against the agent's 4 MiB ceiling. Measured: adding 1.5 MiB
  returns **exit 0**, the history does not move, and the clip is simply gone.
- Under `min-text-item-size`, likewise.
- With `trim-items` on, a whitespace-only clip trims to empty and is dropped. (`trim-items` is
  `false` on this machine today, which is a setting and not a guarantee.)

**A silently lost clip is worse than the blink this whole cycle exists to remove.** The read-back is
what turns all three into a fallback plus a log line.

### 3.5 What the echo bookkeeping actually gains, which is less than an earlier draft claimed

**The comparison in §3.4 is byte-equality.** Stated here because everything below turns on it, and
because any looser rule would be a guess about how GPaste normalises text.

**Safe:** echo suppression rests on the invariant that one text write produces exactly one change
event (`_last_written` is a one-shot, armed only for `KIND_TEXT`). Measured 2026-08-05: `wl-copy`
and `Add` **both raise exactly one `Update` per write** — 10 writes, 10 signals, 10 uuid moves,
identical. The invariant survives the change.

**And no more than that.** An earlier draft said the write path can now arm the echo value "with
the bytes read back, which is what the v3.2 provenance rule has always demanded". **That claim is
empty under a byte-equal criterion:** if the read-back matches, then read-back *is* the written
bytes, and arming with either is the same store. The honest statement is narrower and still worth
having:

- The read-back **confirms delivery**, which `wl-copy` could never do — its own comment in
  `_write_clip` records that re-reading after it would race the hand-off. That is the whole gain,
  and it buys §3.4's silent-loss detection rather than a provenance improvement.
- **The fallback branch keeps today's semantics exactly:** when the tier declines or the read-back
  mismatches, `wl-copy` runs and the echo value is armed with the bytes *written*, because after a
  hand-off there is nothing else to arm it with.

**The mismatch branch must also re-arm `_last_seen` with the top it just read, before calling
`wl-copy`.** GPaste's `do_add_item` moves the history and rolls it back when the selection fails,
which can raise **two** `Update`s for one failed write. The one-shot is consumed by the first
observation whatever it is, so the second would be read as a fresh local change and would send the
*old* top to the Mac — a failed write silently overwriting the Mac's clipboard. Not measured:
provoking a `clipboards_manager_select` failure on a working machine is expensive and the selection
works here. Named and defended rather than left for a production first sighting.

## 4. Rules that are easy to lose

### 4.1 EVERY `gpaste-client` call must reach EOF on stdin — `add` included

`gpaste-client` reads stdin to EOF whenever stdin is **not a TTY**, and under `sshd` it never is.
It does this **before it dispatches the verb**, so this is not a rule about reads:

- Measured: `gpaste-client --version` over ssh **hangs forever**. Reads need `stdin=DEVNULL`.
- Measured: `gpaste-client add` with the body already written and stdin **left open hung for the
  full 5 s probe**, then completed **1.42 s after `close()`**. **EOF is what starts the work, not
  what ends it.** An `add` that writes the body and forgets to close hangs exactly like a `--version`
  that forgets `DEVNULL`.

So the rule is one rule: **write the body or nothing, then close stdin, always.** An earlier draft
of this section said "every call that is not an `add`", which is the narrower claim and would have
left the hang in the one path that carries the user's data.

### 4.1.1 Every call needs a timeout, and `add` needs its own

The hang in §4.1 is caught in production by a timeout and by nothing else — closing stdin is
prophylaxis, not insurance, and a daemon that stops answering produces the same symptom.

- Reads reuse `GPASTE_CALL_TIMEOUT` (`agent/clipwire-agent.py:3289`, currently `3`).
- **`add` needs its own, at least 5 s.** Against a measured 1.41 s the existing 3 s is 2.1x
  headroom, which is a timeout that fires under load rather than one that catches a hang.
- **A timeout is a mismatch**: it takes the §3.4 fallback, like any other failure to confirm.

**And killing the client does NOT cancel the `Add`.** The call is already inside the daemon by then
and the selection completes on its own, so the fallback's `wl-copy` writes the same content a second
time. What that pair does to the `Update` trace — one signal or two, and therefore whether the
one-shot suppression is spent correctly — is **not measured**. It is the narrowest remaining
unknown in this design, it is reachable only through a hang, and it is written down here so the
first person to meet it recognises it.

**Note for whoever touches `GPASTE_CALL_TIMEOUT`:** the comment above it justifies 3 s as "30x
headroom over 103 ms". That justification is now false for the write path — 103 ms was the `gdbus`
fork cost, and this cycle's own call costs 1.41 s.

### 4.2 Never take a body from `GetElementAtIndex`

It returns the display string (§3.2). For text, display happens to equal value — so this is a rule
that testing on text alone will never catch, which is exactly why it is written here.

### 4.3 Non-UTF-8 and embedded NUL never reach the tier — ON THE WRITE SIDE

D-Bus strings must be valid UTF-8, and `gpaste-client` truncates at the first NUL because it is a C
string. Guard before the tier: `body.decode("utf-8")` raising, or `b"\x00" in body`, routes to
`wl-copy`. Both are silent corruptions otherwise — the clip arrives, and it is wrong.

**This guard cannot protect the read direction, and no guard can.** By the time the agent sees a
PC-side clip, GPaste has already ingested and normalised it, so the tier can only return what GPaste
kept. That is a genuine regression against today's `wl-paste`, it is accepted rather than solved,
and it is recorded as such in §5.7 rather than being quietly implied by this section's title.

### 4.4 A refusal that returns 0 is a refusal

`gpaste-client add` returned **exit 0** on the 1.5 MiB clip it discarded. Nothing downstream may
read a zero exit as "the clipboard now holds this". Only the read-back of §3.4 establishes that.

## 5. Accepted residuals, named so they are not rediscovered as defects

v3.3's failure was not technical. It was that its own scope was never restated in terms of what the
owner would still *see*. So:

1. **Images blink, in both directions.** §2.2.
2. **The connect-time reads still blink — by scope, not by necessity.** The connection seed,
   `clipboard_became_ready` and the reconciliation send path call `Clipboard.read()` without
   routing by a history uuid. **They could ask for one:** `gpaste_history_uuid`
   (`agent/clipwire-agent.py:3292`) is a module-level function with no watcher state behind it, so
   nothing prevents those paths from taking the same route. They are left out because they run at
   connect and at reconcile rather than per copy, and because each one sits in reconciliation logic
   that a content change would have to be re-argued through. **This is a deliberate omission with a
   known remedy, not a limit** — an earlier draft of this spec called it a property of the design,
   which would have been false.
3. **A machine without GPaste is unchanged**, blinks included. §2.3.
4. **Mac→PC text is ~1.4 s slower.** §1.4, accepted by the owner.
5. **Clips over 1 MiB − 1 take the `wl-copy` path** and therefore blink. §3.4.
6. **Turning `trim-items` on brings the blink back for a whole class of clips.** It is `false`
   today, and §3.4 already says that is a setting rather than a guarantee. With it on, any clip
   with leading or trailing whitespace trims to something other than what was written, fails the
   byte-equal read-back, and takes the `wl-copy` fallback — correctly, and visibly, forever.
7. **A PC-side clip containing NUL or invalid UTF-8 reaches the Mac in GPaste's normalised form —
   a read REGRESSION against today.** The §4.3 guard protects the *write* direction; on the read
   direction the damage is already done at ingest, because GPaste holds a C string and truncates at
   the first NUL. Today's `wl-paste` hands over the full bytes. This is the one place where v3.4 is
   worse than what it replaces, and detecting it on the read side is deliberately not built (§6).
8. **The read-back opens a window of roughly tens of milliseconds** in which a second PC-side copy
   produces a mismatch, so the fallback's `wl-copy` overwrites it with the Mac's clip. The
   last-writer-wins semantics are unchanged; the window is longer than it was. Accepted.
9. **Clips GPaste does not track still sync through `wl-paste`, and still blink** — as in v3.3 §4.2,
   and now guarded by a test rather than by nobody. The read guard declines the tier on a
   probe-provoked observation over a frozen history uuid (§3.2, 2026-08-17), so this class keeps the
   slow tier's cadence and the slow tier's blink. **One case inside it is not restored:** the guard
   fires only when the history uuid stood still across the whole slow window, so an untracked clip
   landing within one `SAFETY_NET_POLL_SECONDS` window of a *tracked* copy is still answered from
   history and still lost — a narrower residual than the defect it fixes, which lost every untracked
   clip, accepted rather than widened because acting on a single unconfirmed tick is what a one-shot
   can do. Removing the guard does not remove the blink; it replaces the clip with an older one.

**After v3.4, copying text still blinks in exactly one situation the owner will meet: the first read
of a connection.** If that is not acceptable, it belongs in this spec now, not in a report after the
release.

## 6. Acceptance

1. Copying text **on the PC** does not blink, observed by the owner on the real machine.
2. Copying text **on the Mac** does not blink the PC, observed the same way.
3. Copying an **image** still blinks — a pass, not a failure, pinning §2.2 rather than leaving it
   as prose. **And, in the same criterion, the Mac's clipboard must NOT become the text
   `[Image, … ]`.** Without that second half the criterion is inverted by the very bug it should
   catch: reverse the kind check of §3.2 and the image goes through the tier, so the blink
   *disappears* — criterion 3 as first written would have scored that as an improvement while the
   Mac silently received a decoration string instead of a picture.
4. The round-trip corpus, **stated per direction, because the two are not symmetric**:
   - **Mac→PC** — quotes, backslashes, newlines, emoji, whitespace-only, and a 1 MiB − 2 clip all
     arrive byte-identical through the tier. Non-UTF-8 and embedded NUL arrive byte-identical
     *through the fallback*, which is what the §4.3 guard is for.
   - **PC→Mac** — the same corpus byte-identical **except** NUL and non-UTF-8, where the expectation
     is GPaste's normalised form, not the original bytes. §5.7. Writing "byte-identically" here
     without the exception would be a criterion no correct implementation can pass.
   - A **1 MiB + 1** clip must reach the peer **and the fallback's log line must be present**.
     Without pinning the log line the test passes if the tier happened to swallow it — which it
     will the day someone raises `max-text-item-size`.
   - Every corpus case must be shown to travel **through the tier** rather than around it. A test
     that writes with `wl-copy` and reads with `wl-paste` is green against a completely dead tier.
5. **Two separate failure injections, because they break different halves:**
   - **GPaste daemon killed MID-connection.** Killing it *before* connect tests something else
     entirely — `make_watcher` then builds no tier at all, so that arrangement passes while every
     fallback inside the tier is broken.
   - **The daemon alive, the CLIENT broken** (a `gpaste-client` that is missing, or on `PATH` as
     `/bin/false`). This is the only way to exercise the READ fallback: killing the daemon also
     kills the `gdbus monitor` the v3.3 watcher depends on, so the uuid stops arriving and
     `read_text` is never *called* — its fallback would never run, and criterion 5 would pass
     without ever having executed the code it claims to cover. May be met by a unit test with a
     substituted runner rather than a `PATH` shim; the requirement is that the path executes, not
     how it is provoked.
   - The tier must turn **both** failure modes into `None`/`False`: a missing binary raises
     `FileNotFoundError`/`OSError`, a dead daemon returns a non-zero exit, and neither may escape.
6. A machine with no GPaste is byte-identical in behaviour: the diff over `WaylandClipboard` is
   empty, and `make_watcher`'s polling branch constructs nothing new.
7. Every check above is verified **by breaking it**: each test is shown red against the reversion of
   the thing it claims to pin, and the report says what was broken. Three reversions are named here
   because they are the ones a test suite passes over most easily:
   - **reverse the kind check of §3.2** — criterion 3's second half must go red;
   - **delete the read-back of §3.4** — the 1 MiB + 1 case must go red, and it must go red on the
     *loss*, not merely on the missing log line;
   - **leave stdin open after the body in §4.1** — the write must go red by timing out, which is
     also the only test that distinguishes "we close stdin" from "we happen to work".

## 7. The order the work must ship in

The design above describes an end state. Two pairs are **indivisible**, and splitting either leaves
a defect in production for as long as the split lasts:

1. **Switching the write to `Add`** ⊗ **the read-back and its fallback.** A day of writing without
   verification is a day of silently losing every clip over 1 MiB − 1.
2. **Reading bodies through the tier** ⊗ **the kind routing of §3.2.** A day of reading without
   routing is a day of sending `[Image, … ]` to the Mac as text.

The stdin discipline (§4.1) and the timeouts (§4.1.1) belong in the tier's **first** commit, before
its first call — they are not hardening added afterwards; without them the first call hangs.

**The write direction ships before the read direction.** It is self-contained — it does not depend
on the watcher's uuid — so it can be tested Mac→PC in isolation, and it carries the residual the
owner is most likely to notice (§1.4's 1.4 s).

## 8. Evidence and provenance

Measurements: 2026-08-05, on Ubuntu 26.04 / GNOME Shell 50.1 / Wayland / GPaste 45.3, monitor on,
session unlocked, owner present and observing. Source of the blink verdicts is the owner's direct
observation; source of every count and duration is the passive observer
(`.superpowers/sdd/2026-08-03-v3.3-focus-and-recovery/clipwire_observe.py`) or the probe script
recorded with this cycle.

The five failure modes in §3.3, §3.4, §4.1, §4.2 and §4.3 were **predicted by batya from GPaste
45.3's source and then reproduced here**. The predictions are its; the readings are this project's.
Where the two could differ — the attribution of the 1.37 s to `clipboards_manager_select` — the
spec says "inferred" and does not lean on it.

**What batya's review of this spec changed, recorded because the corrections are the useful part:**

- §3.5 claimed a provenance improvement that a byte-equal criterion makes empty. Rewritten to claim
  only what it delivers. This is the project's own measured defect class — prose stronger than code
  — appearing in a document written by someone who had just finished describing that class.
- §4.1 was scoped to "every call that is not an `add`", which is narrower than the failure.
  **Measured after the review:** `gpaste-client add` with the body written and stdin left open hung
  for the full 5 s probe and completed 1.42 s after `close()`. EOF starts the work.
- §4.1.1 (timeouts) did not exist. The spec had no timeout at all, on a design whose headline risk
  is a hang.
- §6.3 would have scored a reversed kind check as an improvement, because removing the blink was
  the only thing it asserted.
- §6.4 demanded byte-identity in a direction where no correct implementation can deliver it.
- §6.5 tested the write fallback twice and the read fallback never.
- Three residuals were missing from §5: `trim-items`, the PC→Mac normalisation regression, and the
  read-back window.
- §7 (order of work) did not exist; two of the pairs it names are indivisible.

Not measured, and named rather than hidden: the `Update` trace when an `add` is killed by its
timeout and the fallback then writes the same content (§4.1.1), and GPaste's rollback path raising
two `Update`s for one failed write (§3.5).

**2026-08-17 measurement session** (`.superpowers/sdd/2026-08-17-v3.4-focus-free-content/measurements.md`,
§2 and §5), recorded because it closes one of the two named unknowns above and leaves the other
exactly where it was:

- **The timeout-then-fallback `Update` trace is now measured, and it is benign — but the two
