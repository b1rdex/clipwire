# clipwire v3.2.1 — splitting the tests, with production frozen

**Date:** 2026-08-02
**Status:** batya-approved
**Amends:** nothing. This release changes no protocol, no format, no observable behaviour and
no shipped artifact. The binary and the agent file it produces are byte-identical to v3.2's.

This is the mirror of v3.0.1, and the second half of a sequence that release declared: **cycle N
splits production with the tests frozen; cycle N+1 splits the tests with production frozen.**
Both halves get the same evidence, neither gets it at the same time as the other.

## Why this exists

Three test files grew past the point where a reviewer can hold them:

| file | lines |
|---|---|
| `agent/tests/test_watcher.py` | 3968 |
| `Tests/clipwireTests/HandleFrameTests.swift` | 2165 |
| `Tests/clipwireTests/PairingHarnessTests.swift` | 1539 |

The justification is v3.0.1's, unchanged: three of the defects that reached production lived
*between* two changes that were each correct and each independently reviewed, and that failure
mode gets likelier as the distance between related code grows. Tests are where this project
does most of its reasoning, so the argument applies to them at least as strongly.

## The criterion, decided first, because it picks the split mechanism

### The obvious mirror is not a mirror, and alone it is worthless

The tempting statement of this release's rule is v3.0.1's with the sides swapped:

> `git diff` of `Sources/` and `agent/clipwire-agent.py` across the branch is empty.

**That is far weaker than the rule it imitates, and taken alone it proves nothing.** In v3.0.1
the frozen *tests* were the witness: production could be restructured freely because an
unchanged suite still passing is evidence about production's behaviour. Here the frozen thing is
production, and frozen production is a witness to nothing about the tests. A split can delete a
test, rename it out of discovery, mark it `skip`, or gut an assertion to `XCTAssertTrue(true)`,
and "the production diff is empty" stays true through every one of those.

So the frozen-production diff is necessary and is **leg one of four**. The other three are what
actually carry the release.

### Leg 2 — the (class, method) multiset, taken from the runner

The invariant is the **multiset of `(class, method)` pairs**, not the count and not the full
test ID.

The full ID cannot be used: in Python it embeds the module name, and changing the module name is
exactly what a split does, so every moved test's ID changes for a reason that means nothing. The
pair survives, because classes move whole. A multiset rather than a set, so that two like-named
classes in different modules cannot collapse into one and hide a loss.

Three requirements, each closing a way this leg bends:

- **The pairs come from the runner, never from a grep of the sources.** Python:
  `python3 -m unittest discover -s agent/tests -v`, the command CI runs
  (`.github/workflows/ci.yml:77`). Swift: `swift test list`, which emits exactly 278 lines of
  `clipwireTests.Class/method` today. A grep cannot see a test that stopped being discovered,
  and loss of discovery is half of what this leg exists to catch.
- **Green is stated as `failures=0, errors=0, skipped=0`**, explicitly. A pair set does not
  distinguish a test that ran from one that was skipped.
- **The baseline is derived by machine from the merge-base, not transcribed.** See below.

### Leg 3 — a total reconstruction manifest

v3.0.1 proved each move was a permutation by rebuilding the original file from its pieces and
diffing byte-for-byte against the committed blob. That technique transfers, with one change
forced by a fact of both languages: **a split file cannot be a pure byte-slice**, because each
new file needs its own header — imports in Python, `import XCTest` / `@testable import clipwire`
and an `extension HandleFrameTests {` wrapper in Swift.

So each new file is declared as **scaffold + a list of intervals of the original blob**, and the
manifest is checked for **totality, not merely coverage**:

1. Concatenating every interval from every file, in original order, reproduces the original blob
   **byte for byte**.
2. The intervals are **pairwise disjoint** and their union is **the whole file**, `[1, N]`.
3. Everything outside an interval is scaffold, and every scaffold line is drawn from a closed,
   declared set. **That set lives in the manifest itself**, not in this document and not in the
   checker — so the artifact a reviewer reads and the artifact the tool checks are one thing.

Totality is the point. "Every piece ended up somewhere" does not exclude a deletion; a partition
of the original does. Under a total manifest **`HandleFrameTests.swift`'s evidence is not weaker
than the other two files'** — an earlier draft of this spec conceded that it was, and the
concession was wrong. It described an incomplete manifest, not a weaker proof.

### Leg 4 — three mutants, each killed through code that moved

A suite can satisfy every leg above and still have been quietly detached from the code. The
check is the project's own rule — *verify a check by breaking it* — applied to the split itself:
introduce a defect, confirm the suite reds, restore.

One mutant per split file, and **the killing test must depend on something the split moved.** A
mutant killed entirely by code that did not move says nothing about the split.

"Depends on something that moved" rather than "is itself a test that moved", because the two
Swift files move opposite things and the narrower rule is unsatisfiable for one of them.
`HandleFrameTests` moves *tests* out to shards, so its mutant must be killed by a shard.
`PairingHarnessTests` moves the *harness* while every test stays in the anchor — so no test
moves at all there, and the rule that carries the meaning is that the killing test runs
**through** the moved `PairingHarness`. Both are the same claim: the mutant's death certificate
passes through relocated code.

| mutant | file | killer, and what it proves moved |
|---|---|---|
| delete one line of `Channel`'s pipe handling | `Sources/clipwire/Channel.swift` | any `PairingHarnessTests` case — every one runs through the moved `PairingHarness` |
| break the `.imageClip` apply branch | `Sources/clipwire/HandleFrame.swift` | `testAnImageClipIsAppliedToThePasteboardAsAnImage`, in the moved image shard |
| break the filter in `parse_gpaste_line` | `agent/clipwire-agent.py` | `TestGPasteSignalParsing.test_accepts_the_real_captured_signal`, in the moved signal-parsing shard |

Each killer is named, not left as "some test in that file" — otherwise "killed by moved code" is
unverifiable.

The Python mutant is deliberately **not** `write_clip`'s decode, which is the obvious choice:
`TestWriteClipDecodesTheWirePayload` and `TestEchoBookkeeping` both stay in the anchor by the map
rule below, so that mutant would die entirely in unmoved code and prove nothing about the split.
The first draft of this table made exactly that mistake — **the map constraint and this leg pull
in opposite directions, and nothing in the design notices the collision on its own.**

Mutants are applied to a scratch working copy and never committed.

### The commit chain, because "the original blob" stops being one thing

The four legs above compose only if the branch's shape is pinned. It is not enough to name them:
this branch lays **more than one layer on the same file**, and the moment it does, "reconstruct
the original blob byte-for-byte" has no single referent. Two concrete contradictions in the first
draft, neither visible from any single rule:

- The widening commit changes 11 lines of the two Swift files. If the manifest binds to the
  **merge-base** blob, byte reconstruction of both Swift files is then *required to fail*.
- Repairing the inherited debts at `HandleFrameTests.swift:1621` and `:1676` edits lines that sit
  inside intervals bound for the status-and-logging shard. Repair after the split and the
  manifest stops converging; repair before it and the manifest must bind to the post-repair blob
  — which the first draft never said.

So the chain is declared, and every check names the revision it binds to:

```
merge-base
  → C1  repair the four inherited comment debts (test files only; pairs and green unchanged)
  → C2  widening — the 9 modifier removals; the modifier script binds C1→C2
  → C3… one split commit per file; each file's manifest binds to that file's blob
         at the PARENT of its own split commit
  → after its split commit, none of the three files is edited again on this branch
```

**A fact that makes this safe rather than merely ordered: widening and comment repair both change
the content of lines without changing their number.** So interval numbering is stable across both
layers, and a manifest computed against the merge-base file remains valid against C2's.

That property is asserted here and **checked, not trusted**: C1 and C2 must each leave
`wc -l` of every file they touch unchanged.

### The baseline must be a witness, not a transcription

The numbers in this document — Swift 278, Python 356, fakes 29 — were measured today, but a
number typed into a spec is a claim the spec makes about itself. The acceptance script therefore
**derives the baseline itself**: `git worktree` at the merge-base, run both suites there, collect
the pair multisets, then compare against the branch. This is v3.0.1's "rebuild from the committed
blobs, not from the working copy" applied to counts instead of bytes.

### Where the checker lives

`scripts/`, committed, next to `comment_only.py` — an auditable artifact of the release rather
than something one person can run on one machine.

**It cannot be an in-suite test this cycle, and that is a consequence of the criterion rather
than a preference.** A new test file adds pairs to the multiset and so breaks the very equality
it would be checking. Promoting a slimmed guard into the suite is the next cycle's material.

**And it is not wired into CI either, for a second and independent reason.** Each manifest binds
to a `blob` revision among this branch's own commits, and this project merges squash — v3.0.1
went in as the single commit `f3af3e4`. After the merge those revisions are unreachable from
`main`, so a standing CI step would fail forever on its first post-merge run; a shallow
`actions/checkout` would break it even on the branch. The manifests are therefore **branch-local
release evidence**, verified at review, where the evidence is actually consumed. That lands in
the same place as the argument above: the verifier does not become a standing guard this cycle.

**"Branch-local" is meant literally: the manifests are deleted before the merge.** Left in place
they would sit on `main` as files that look like a check and cannot run one — their `blob`
revisions no longer resolve, so `split_manifest.py verify` would fail for a reason that says
nothing whatever about the code. This project has been bitten repeatedly by instruments that
answer confidently about something they never measured, and a permanently unverifiable proof is
that same shape at rest. The partition was proved when it mattered; the record of *that* belongs
in the release report, not in a file pretending it can re-derive it.

**They also may not live inside a build or discovery target.** A manifest committed under
`Tests/clipwireTests/` makes SwiftPM emit `found 1 file(s) which are unhandled`, and the ordinary
fix — `exclude:` in the target declaration — is unavailable because `Package.swift` is frozen. So
they live in `docs/superpowers/manifests/2026-08-02-v3.2.1-test-split/`: tracked, so a reviewer
meets them in the diff; beside the spec and plan that explain them; and reachable by neither
SwiftPM's `path:` nor `unittest discover`'s glob. The first draft said "committed beside each
split", which put them inside the target and produced a warning no frozen-`Package.swift` cycle
can silence.

The frozen path set, declared explicitly so no check has to infer it: `Sources/**`,
`agent/clipwire-agent.py`, `Package.swift`, `fixtures/**`, `Tests/fakes/**`.

## Execution order — measured before the spec, because a split changes it

Every leg above is static, and a test split changes the *dynamic* of a run. Module and file
boundaries are execution order, and order is behaviour. Both halves were measured on unsplit
code, so that a red after the split can be compared against a control rather than blamed on
flake.

**Swift: an extension split cannot change the order at all.** XCTest executes a class's methods
in **case-insensitive name order, independent of which file declares them**. Measured twice:
first by confirming that the observed order of `HandleFrameTests`'s 78 methods matches
`sorted(key=str.lower)` exactly and ASCII order not at all; then by breaking it — three methods
added to `BackoffTests` from *another* file, named to interleave, executed as
`testAaa…, testReset…, testSaa…, testSequence…, testZzz…`. Interleaved by name, not grouped by
file. The risk is therefore eliminated by construction, not merely unobserved.

**Python: the order does change, and the suite is order-independent anyway.** `unittest` sorts
modules alphabetically, so new module names reorder the run. Measured on unsplit code: all 356
pass **reversed**, and under **three independent shuffles** (seeds 1, 7, 42), with
`failures=0 errors=0 skipped=0` each time; and all **57 test classes pass in isolation**, one
process each. Class-level isolation is the stronger of the two — it removes every cross-class
carry-over rather than one permutation of it.

**Module headers execute once per module and are side-effect free.** `test_watcher.py:1-63` is
imports and constants; `agent_under_test` caches the loaded agent in `sys.modules`, so shards
importing it do not re-execute the agent.

## Part 1 — the split maps

### The rule that shapes all three maps: production comments are frozen too

Eight production comments name test files or test classes that this release moves. Production is
frozen, so **the release cannot repair a bearing it breaks** — the same shape as v3.0.1's
discovery that its criterion outlawed its own enforcement.

The resolution is to **constrain the map so that nothing production names is falsified**, rather
than to buy freedom with a carve-out. A carve-out would put an exception into the central claim,
in prose — the exact channel this project has measured as the one its audits miss. The
constraint is cheap here because the subjects it pins together are cohesive anyway.

Two mechanisms make it work:

- **Each anchor keeps its original file name.** `HandleFrameTests.swift` and `test_watcher.py`
  continue to exist; shards are new files beside them. A reference to the *file* stays true if
  its subject stays in the anchor.
- **A class named from a frozen file stays in its anchor.** For Swift this is free — extensions
  preserve the class name, so `Freshness.swift:88`'s "the two `HandleFrameTests` cases" survives
  wherever those cases live.

| production reference | names | resolution |
|---|---|---|
| `Freshness.swift:88` | the class `HandleFrameTests` | true anywhere — extensions preserve it |
| `HandleFrame.swift:25` | the file; subject = ordering assertions | arm-before-write cases stay in anchor |
| `ClipStateAnnouncement.swift:14` | the file; subject = the `sha256Hex` known vector | that case stays in anchor |
| `ClipStateAnnouncement.swift:196` | the file; subject = `announceClipState` send spy | those cases stay in anchor |
| `LocalChange.swift:51` | the file; subject = the outgoing frame | those cases stay in anchor |
| `Pasteboard.swift:25` | the file; subject = the write-side spy | `RecordingPasteboard` stays in anchor |
| `Pasteboard.swift:304` | the file; subject = arm-before-write | as above |
| `agent/clipwire-agent.py:2586` | `test_watcher.py`'s `TestWriteClipDecodesTheWirePayload` **and** `TestEchoBookkeeping` | both classes stay in the anchor |

Two *test* files also name `test_watcher.py` — `test_source_layout.py:21`
(`TestModuleDefinitionOrder`) and `test_fixtures.py:138`
(`TestWriteClipDecodesTheWirePayload.test_stores_the_literal_known_hash_for_a_pinned_vector`).
Those are repairable, since tests are not frozen this cycle, but both subjects stay in the anchor
anyway and no repair is needed.

**Consequence, recorded as debt rather than fixed:** those six production comments still point at
a *file*, which is the bearing shape that rots. Repairing them to name the test *class* — durable
under any future split, since the criterion preserves `(class, method)` — is a comment-only
change to production and belongs to the next cycle that is allowed to touch it.

**This constraint is the price of *this* cycle, not a standing invariant, and saying so is not a
formality.** Left unqualified, it hands production comments a permanent veto over test topology:
any future reorganisation would be pre-constrained by whatever prose happens to name a test file.
The debt above is what retires it — once those six bearings name classes instead of files, the
constraint dissolves, because a class reference survives any split this criterion permits.

### `PairingHarnessTests.swift` — a clean top-level permutation

| file | intervals of the original | lines |
|---|---|---|
| `PairingHarnessTests.swift` (anchor) | header + `PairingHarnessTests` | ~539 |
| `PairingHarness.swift` | `PairingHarness`, the `String` extension, `exportEnvironment`, `HarnessPasteboard` | ~1000 |

**Two files, not three, and the reason is a measurement rather than taste.** `exportEnvironment`
and `String.occurrences(of:)` are called only from inside `PairingHarness` — nowhere else in
`Tests/` — so they travel with it and **stay `private`**. A third support file would have forced
both to widen for no gain, which is v3.0.1's rule still standing: *move the boundary, not the
modifier.*

`PairingHarness` stays one class at ~916 lines. Splitting a class is a different kind of change
from moving one, and this release does not make it — the same reasoning that left `class Agent`
and `handleFrame` whole through v3.0.1.

### `HandleFrameTests.swift` — extensions, because the criterion chose them

The file is one 2165-line class, so it is not a top-level permutation in any sense. Three
mechanisms were available:

- **New sibling class names** (`HandleFrameImageTests`) — **rejected**: it breaks leg 2 outright.
  The `(class, method)` multiset is the release's strongest evidence and this mechanism destroys
  it to gain nothing.
- **A shared base class** — **rejected**: XCTest runs a base's test methods once per subclass, so
  the count inflates and the pair multiset gains members that never existed.
- **Extensions in new files** — **chosen**, and measured: the methods are discovered, the test ID
  keeps the original class name, and execution order is unchanged (above).

The anchor keeps the class declaration, the nested `RecordingPasteboard`, all stored properties,
and the seven shared helpers. Shards are `extension HandleFrameTests { … }`. A helper used by
exactly one shard **moves into that shard and stays `private`**.

| file | subject | approx. source span |
|---|---|---|
| `HandleFrameTests.swift` (anchor) | header, `RecordingPasteboard`, shared helpers, incoming-clip application and arm-before-write, outgoing frame and local change, `sha256Hex` vector, `announceClipState` basics | 1-308, 993-1222 |
| `HandleFrameHelloTests.swift` | hello replies, skew, announcement gating | 309-576 |
| `HandleFrameClipStateTests.swift` | clip-state resolution, the send branch, size limits | 577-992 |
| `HandleFrameStatusAndLoggingTests.swift` | peer state vs. our announcement, `reportsUp`, reconciliation and failed-save logging | 1223-1754 |
| `HandleFrameImageTests.swift` | incoming image clips | 1755-2002 |
| `HandleFrameProvenanceTests.swift` | substitution and origin (v3.2's material) | 2003-2165 |

Spans are approximate here and **exact in the plan**; the manifest is what binds.

### `test_watcher.py` — shards around a constrained anchor

28 top-level declarations, all contiguous spans. The anchor keeps lines 1-63 (imports and
constants) and the two classes `agent/clipwire-agent.py:2586` names, plus
`TestModuleDefinitionOrder`, which is about the agent's own layout and belongs beside the header
that reads it. The anchor is therefore **not one contiguous span**, which the interval manifest
handles by construction.

Shards take the remaining spans, grouped by subject: GPaste signal parsing and watcher lifecycle;
`pdeathsig`; the polling watcher; the safety net; `make_watcher` and lifecycle wiring;
local-change race safety; incoming clip state; provenance.

**Every shard is named `test_watcher_<subject>.py`**, and that prefix is load-bearing twice over.
`agent/tests/` already contains `test_lifecycle.py`, so a shard called `test_lifecycle.py` for
"`make_watcher` and lifecycle wiring" would collide with an existing, unrelated module — a
name-shaped bug in a release whose whole claim is that nothing was lost. The prefix also keeps
the shards adjacent to their anchor in discovery order, which is alphabetical.

**Constants are not duplicated.** `HASH_A`/`HASH_B` carry meaning (their sort order is what the
freshness tie-break depends on) and `GPASTE_UPDATE_LINE` is a verbatim capture from the target
machine. Copying them into five files manufactures a drifting truth, which is this project's
signature defect shape. The anchor keeps them and shards do `from test_watcher import …`.
Measured, not assumed: a shard importing named constants from its anchor resolves under
`python3 -m unittest discover -s agent/tests`, because discover puts the start directory on
`sys.path`.

**Shards import named constants only, never `from test_watcher import *`** — a star import would
pull the anchor's `TestCase` subclasses into the shard's namespace and `unittest` would discover
and run them twice, inflating the multiset.

## Part 2 — visibility, as a closed budget

v3.0.1's rule was absolute: no access modifier may be widened. **It does not transfer, and the
reason it does not is worth stating rather than assuming** — it was justified by production
encapsulation, and a test target has no such interest. Extensions relocate the problem rather
than removing it: `private` members are unreachable from an extension in another file, measured.

The replacement is not permission but a budget — **exactly nine lines, named here, and nothing
else. Each of the nine was measured, not assumed:**

- `HandleFrameTests.swift` (7): `tempStatusURL`, `tempLogPath`, `tempLog`, `loggedMessages`,
  `hashA`, `hashB`, `tempClipStateStore`. Every one of the seven has call sites **outside** the
  anchor's intervals — checked per helper, not inferred from "these look general".
- `PairingHarnessTests.swift` (2): `PairingHarness` and `HarnessPasteboard`.

**`HarnessPasteboard`'s widening is forced by a Swift rule, and it is the kind of thing this
budget exists to expose.** The tests reach `harness.pasteboard` at eight sites, and
`pasteboard` is an internal member of `PairingHarness`; Swift forbids an internal member whose
type is `private`. So widening the harness drags its pasteboard's visibility with it. A budget
written from the four top-level `private` keywords — the obvious reading, and the one the first
draft took — would have been wrong in both directions at once: too many, because
`exportEnvironment` and the `String` extension stay private, and too few, because it misses a
widening no `private` keyword at top level announces.

The remaining private members — `unsaveableStore`, `persistFailures`, `heldImage`,
`returnedImage`, `macsOriginal`, `pcsReEncode`, and all of `HarnessPasteboard`'s stored fields —
are used by one destination each, move with it, and stay `private`.

The widening lands in **one commit, C2 in the chain above** — after the comment-debt repairs and
before any split — so that every split commit is a pure
move. A script checks it: every changed line equals the old line minus a leading `private ` or
`fileprivate `; nothing added, nothing deleted, no modifier written in (`internal` is the default
and is never spelled).

**One hazard, checked before that commit lands:** `private extension String` becoming internal
exposes its members to the whole test target. The four widened names and the String extension's
members are grepped across `Tests/` for collisions first.

## What this release does not do

- **No new abstractions, no deduplication.** No shared fakes file, no helper consolidation, no
  "while we are here". The permitted additions are the scaffold set and nothing else. A reviewer
  will be tempted; the answer is that behaviour cycles come later.
- **`Package.swift` is not touched.** The test target is declared by `path:` and SwiftPM
  discovers sources beneath it; `unittest discover` globs `test_*.py`. Verified, and recorded so
  that nobody "fixes" it and breaks the frozen-production claim.
- **`class Agent` and `handleFrame` are not decomposed.** Still their own cycles.
- **`Tests/fakes/` is frozen** along with production. The fakes are the harness's instrument, and
  freezing them keeps the mutant checks interpretable.
- **The four comment debts inherited from v3.0.1 are repaired**, since test files are writable
  this cycle: `FrameTests.swift:104`, `HandleFrameTests.swift:1621` and `:1676`,
  `LogTests.swift:13`. Repaired to a **symbol**, never a position. They land in **C1, before any
  split**, because two of them sit inside intervals bound for a shard: repairing them afterwards
  would edit a file the chain has already declared finished.

## Acceptance

1. **The production diff is empty**, over the whole branch:
   `git diff --stat main...HEAD -- Sources/ agent/clipwire-agent.py Package.swift fixtures/ Tests/fakes/`
   prints nothing. Leg 1.
2. **The `(class, method)` multiset is identical** to the merge-base's, both suites, with the
   baseline derived by the script from a worktree rather than read from this document. Both runs
   report `failures=0 errors=0 skipped=0`.
3. **The manifest is total**: intervals disjoint, union `[1, N]`, and concatenation byte-identical
   to that file's blob **at the parent of its own split commit** — not to the merge-base, which
   C1 and C2 have already changed by design.
4. **The widening commit is exactly 9 lines**, each a modifier removal, verified by script; and
   **C1 and C2 each leave `wc -l` unchanged** on every file they touch, which is what keeps the
   interval numbering valid across both layers.
5. **All three mutants red the suite, each through code that moved**, by the named killing test
   in the leg-4 table, and the tree is clean afterwards.
6. **Every leg holds at every commit**, not only at the branch tip, so a bisect means something.
7. **CI green** — Swift on `macos-latest`, Python on 3.11, 3.13, 3.14.
8. **No hardware smoke, and this is a decision rather than an omission.** v3.0.1 needed one
   because restructuring production can break initialisation order and startup timing, which no
   test reaches. Here the shipped artifact is byte-identical by acceptance item 1, so a smoke has
   no subject: there is nothing it could detect that the frozen diff has not already excluded.
   The locked-PC problem does not arise.
